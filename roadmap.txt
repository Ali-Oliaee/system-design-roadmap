# Concepts & Glossary

## Networking & Protocols | network | concept
[ ] OSI vs TCP/IP model :: Layered mental model: physical, link, network, transport, session, presentation, application. Useful for locating a bug at the right layer.
[ ] Frame :: Layer-2 unit of data (Ethernet/Wi-Fi). Carries a MAC source/destination and a payload; bounded by MTU.
[ ] Packet :: Layer-3 unit (IP). Has source/destination IP addresses and TTL; routed hop by hop across networks.
[ ] Segment / Datagram :: Layer-4 unit: TCP calls it a segment, UDP calls it a datagram. Carries ports and sequence info.
[ ] MTU / MSS :: MTU is the largest frame a link accepts (typically 1500 bytes); MSS is the largest TCP payload that fits without fragmentation.
[ ] Three-way handshake :: SYN, SYN-ACK, ACK — TCP connection setup. Costs one RTT before any data flows.
[ ] TCP vs UDP :: TCP: ordered, reliable, congestion-controlled. UDP: fire-and-forget, no ordering — better for real-time media and games.
[ ] Head-of-line blocking :: One stalled item blocks everything behind it — in TCP streams, in HTTP/1.1 pipelines, and in single-partition queues.
[ ] QUIC / HTTP-3 :: UDP-based transport with built-in TLS, independent streams (no TCP head-of-line blocking) and 0-RTT resumption.
[ ] QoS (Quality of Service) :: Traffic prioritization and shaping: classify, mark (DSCP), queue, and police traffic so latency-sensitive flows win under congestion.
[ ] Jitter :: Variance in packet arrival time. Voice/video use jitter buffers to smooth it; average latency alone hides it.
[ ] Bandwidth vs throughput vs goodput :: Capacity of the pipe vs what actually flows vs useful application bytes after overhead and retransmits.
[ ] TTL (time to live) :: Hop counter on an IP packet that prevents routing loops. Also used generically for cache/DNS expiry.
[ ] NAT :: Network Address Translation maps many private IPs to one public IP — the reason IPv4 survived, and why P2P needs hole punching.
[ ] CIDR / subnet :: Address block notation (10.0.0.0/16). Defines how many hosts fit and where routing boundaries sit.
[ ] ARP :: Resolves an IP address to a MAC address on the local link. ARP spoofing is a classic LAN attack.
[ ] DNS resolution :: Recursive resolver, root, TLD, authoritative servers. A/AAAA, CNAME, MX, TXT, NS, SRV records; TTL controls caching.
[ ] Anycast :: One IP advertised from many locations; BGP routes each user to the nearest instance. Backbone of CDNs and public DNS.
[ ] Unicast / Broadcast / Multicast :: One-to-one, one-to-all on a segment, one-to-a-group. Multicast is how IPTV and service discovery scale.
[ ] Keep-alive :: Reusing an open TCP/HTTP connection across requests to avoid repeated handshakes.
[ ] Ping / Pong :: Liveness heartbeat frames (WebSocket control frames, or ICMP echo). If a pong does not arrive within the deadline, the peer is presumed dead.
[ ] TLS handshake :: Negotiates cipher, verifies the certificate chain, and derives session keys. TLS 1.3 does it in one RTT (or zero on resumption).
[ ] mTLS :: Both client and server present certificates. Standard for service-to-service auth inside a mesh.
[ ] SNI / ALPN :: TLS extensions: SNI says which hostname you want, ALPN negotiates the protocol (h2, h3) inside the same handshake.
[ ] Proxy vs reverse proxy :: Forward proxy acts for the client; reverse proxy acts for the server (TLS termination, routing, caching, WAF).
[ ] Load balancer L4 vs L7 :: L4 balances TCP/UDP flows; L7 understands HTTP and can route by path, header, or cookie.
[ ] Sticky sessions :: Pinning a client to one backend. Simple but harms elasticity — prefer externalized session state.
[ ] Congestion control :: Cubic, BBR: algorithms that adapt send rate to observed loss/latency to avoid collapsing the network.
[ ] Nagle algorithm :: Batches small TCP writes to reduce overhead; adds latency, so interactive protocols disable it (TCP_NODELAY).

## Real-Time & Messaging | chat | concept
[ ] Short polling :: Client asks "anything new?" on a fixed interval. Simple, wasteful, and always at least one interval stale.
[ ] Long polling :: Server holds the request open until data arrives or a timeout fires. Near real-time without a persistent protocol.
[ ] SSE (Server-Sent Events) :: One-way server-to-client stream over plain HTTP with automatic reconnect and event IDs. Ideal for feeds and notifications.
[ ] WebSocket :: Full-duplex connection upgraded from HTTP. Frames flow both ways with no request/response overhead.
[ ] WebSocket frame :: The unit a WebSocket sends: opcode (text/binary/close/ping/pong), mask, payload length, payload. Messages can span multiple frames.
[ ] Message vs frame :: A message is the logical payload the app cares about; frames are the transport chunks it is split into and reassembled from.
[ ] Ping/pong (heartbeat) :: Periodic control frames that prove the socket is alive and keep intermediaries from idling it out.
[ ] Reconnect with backoff :: On disconnect, retry after exponentially growing, jittered delays — plus resume-from-last-event-id so nothing is lost.
[ ] WebRTC :: Peer-to-peer media/data with STUN/TURN for NAT traversal. Lowest latency, highest operational complexity.
[ ] Webhook :: Server-to-server HTTP callback. The receiver must verify signatures, be idempotent, and respond fast.
[ ] Polling vs webhooks :: Pull vs push. Polling is simple and controllable; webhooks are efficient but demand a public, reliable, idempotent endpoint.
[ ] Pub/Sub :: Publishers emit to a topic; subscribers receive independently. Decouples producers from consumers.
[ ] Message queue vs event stream :: A queue delivers a job to one consumer and deletes it; a stream is a durable, replayable log many consumers read at their own offsets.
[ ] Command vs event vs message :: A command asks for something to happen; an event states something happened; a message is the envelope carrying either.
[ ] Consumer group / offset :: Partitions are split across a group; each consumer commits an offset marking how far it has processed.
[ ] At-most-once / at-least-once / exactly-once :: Delivery guarantees. Exactly-once end-to-end is really at-least-once delivery plus idempotent processing.
[ ] Ack / nack / visibility timeout :: Acknowledge to remove a message; nack or let the timeout expire to redeliver it to another consumer.
[ ] DLQ (dead letter queue) :: Where poison messages land after N failed attempts, so one bad payload cannot stall the pipeline.
[ ] Fan-out :: One event delivered to many consumers or timelines. Fan-out-on-write precomputes; fan-out-on-read computes at query time.
[ ] Ordering guarantees :: Usually only per-partition/per-key. Global ordering costs throughput — pick a partition key that matches your ordering need.
[ ] Backpressure :: Signaling upstream to slow down when the consumer cannot keep up, instead of buffering until memory dies.
[ ] Outbox pattern :: Write the domain change and the outgoing event in one DB transaction; a relay publishes it. Removes dual-write inconsistency.
[ ] Idempotent consumer :: Deduplicates by message ID so redelivery does not double-charge or double-send.
[ ] Replay / reprocessing :: Rewinding the log to rebuild state or fix a bug. The main reason to prefer a stream over a queue.
[ ] Presence :: Tracking who is online. Usually heartbeat + TTL key in Redis, with a grace window to avoid flapping.

## API Design & Reliability | globe | concept
[ ] Idempotency :: The same request applied twice has the same effect as once. GET/PUT/DELETE are idempotent by definition; POST is not.
[ ] Idempotency key :: A client-generated unique key stored server-side with the first response, so a retried payment or order never duplicates.
[ ] Safe vs unsafe methods :: Safe methods (GET, HEAD, OPTIONS) must not change state — proxies and crawlers assume this.
[ ] Pagination: offset vs cursor :: Offset is easy but drifts and slows on deep pages; cursor/keyset is stable and index-friendly.
[ ] Rate limiting :: Token bucket (bursty), leaky bucket (smooth), fixed window (cheap, edge spikes), sliding window (accurate).
[ ] Throttling vs quota :: Throttling shapes short-term rate; quota caps consumption over a billing period.
[ ] 429 + Retry-After :: The correct way to reject an over-limit caller and tell it exactly when to come back.
[ ] Exponential backoff with jitter :: Retry delays double and are randomized, so a thousand clients do not retry in lockstep and cause a thundering herd.
[ ] Retry storm :: Retries amplifying an outage. Bound them with budgets, jitter, and circuit breakers.
[ ] Circuit breaker :: Closed, open, half-open. After repeated failures it stops calling the dependency, then probes for recovery.
[ ] Bulkhead :: Isolated resource pools per dependency so one slow downstream cannot exhaust every thread.
[ ] Timeout budget :: A total deadline propagated down the call chain, so nested calls cannot exceed the caller patience.
[ ] Graceful degradation :: Serving a reduced-but-useful response (cached, partial, default) instead of an error when a dependency is down.
[ ] Fail-open vs fail-closed :: On failure, allow (availability first) or deny (safety first). Auth fails closed; recommendations fail open.
[ ] ETag / If-None-Match :: A content fingerprint enabling 304 Not Modified responses and optimistic concurrency on writes.
[ ] Conditional requests :: If-Match / If-Unmodified-Since prevent lost updates when two clients edit the same resource.
[ ] CORS / preflight :: The browser same-origin policy plus an OPTIONS handshake that authorizes cross-origin calls.
[ ] Content negotiation :: Accept, Accept-Language, Accept-Encoding let one URL serve JSON, HTML, or a compressed variant.
[ ] API versioning :: URI (/v2), header, or media type. The real rule: never break a shipped contract; add, deprecate, then remove.
[ ] Backward vs forward compatibility :: Old clients keep working with new servers; new clients tolerate old servers. Protobuf/Avro schema rules encode this.
[ ] BFF (backend for frontend) :: A per-client API layer that shapes and aggregates data for web, mobile, or partners.
[ ] API gateway :: Single entry point handling routing, authN, rate limits, quotas, and observability for many services.
[ ] REST vs GraphQL vs gRPC vs SOAP :: Resource-oriented, query-driven, contract-first binary RPC, and legacy XML enterprise messaging.
[ ] HATEOAS :: Responses embed links to next actions. Rarely implemented fully, useful as a discoverability idea.
[ ] Batching / request coalescing :: Merging duplicate or related in-flight requests into one to cut load and latency.
[ ] Deadline propagation :: Passing the remaining time budget in metadata so downstream work is abandoned when the client already gave up.

## Data & Storage | db | concept
[ ] Soft delete :: Mark a row deleted (deleted_at) instead of removing it. Preserves history and referential integrity, but every query must filter it.
[ ] Hard delete :: Physically remove the row. Required for GDPR erasure; irreversible without backups.
[ ] Tombstone :: A delete marker written to a log or replica set so the deletion propagates; garbage-collected later (compaction/vacuum).
[ ] ACID :: Atomicity, Consistency, Isolation, Durability — the transactional guarantees of a classic RDBMS.
[ ] BASE :: Basically Available, Soft state, Eventually consistent — the pragmatic alternative for large distributed stores.
[ ] CAP theorem :: Under a network partition you choose consistency or availability. Not a license to abandon consistency when healthy.
[ ] PACELC :: Extends CAP: on Partition choose A or C, Else choose Latency or Consistency. Describes normal operation too.
[ ] Isolation levels :: Read uncommitted, read committed, repeatable read, serializable — each removes another anomaly class at a throughput cost.
[ ] Anomalies :: Dirty read, non-repeatable read, phantom read, lost update, write skew. Know which level prevents which.
[ ] MVCC :: Multi-version concurrency control: readers see a snapshot instead of blocking on writers. How Postgres avoids read locks.
[ ] Optimistic locking :: Assume no conflict; check a version column at write time and reject stale updates.
[ ] Pessimistic locking :: Take the lock up front (SELECT FOR UPDATE). Safe under high contention, but risks deadlocks.
[ ] Deadlock :: Two transactions each holding what the other needs. Fix with consistent lock ordering and short transactions.
[ ] Index (B+Tree) :: Sorted structure enabling range scans and ordered reads; the default index in relational databases.
[ ] LSM tree :: Write-optimized structure using memtables, SSTables, and compaction. Powers RocksDB, Cassandra, ScyllaDB.
[ ] Covering index :: An index that contains every column the query needs, so the table itself is never touched.
[ ] Cardinality / selectivity :: How distinct a column is. Low-cardinality columns rarely deserve their own index.
[ ] N+1 query :: One query for a list plus one per row. Fix with joins, IN batching, or DataLoader-style batching.
[ ] Connection pool :: A bounded set of reusable DB connections. Too small starves the app; too large melts the database.
[ ] Sharding :: Splitting data across independent databases by key. Choose the shard key for even distribution and query locality.
[ ] Hot partition / hotspot :: One shard or key taking a disproportionate share of traffic. Fix by salting keys or re-sharding.
[ ] Consistent hashing :: Maps keys to a ring of nodes so adding or removing a node only moves a small fraction of keys.
[ ] Partitioning: vertical vs horizontal :: Vertical splits columns/tables by concern; horizontal splits rows by key.
[ ] Replication lag :: Delay before a replica reflects a primary write. Causes read-your-own-writes bugs — route those reads to the primary.
[ ] Quorum (R + W > N) :: Reading and writing overlapping subsets of replicas gives strong-enough consistency without contacting all of them.
[ ] WAL (write-ahead log) :: Durability mechanism: append the change to a log before applying it. Also the basis of replication and CDC.
[ ] CDC (change data capture) :: Streaming committed row changes out of the log into other systems (search, cache, warehouse).
[ ] Bloom filter :: Probabilistic set membership: no false negatives, some false positives. Skips useless disk reads in LSM stores.
[ ] Materialized view :: A precomputed, stored query result refreshed on a schedule or incrementally. Trades freshness for read speed.
[ ] Denormalization :: Duplicating data to avoid joins on the read path. Buys latency, costs write complexity and consistency.
[ ] OLTP vs OLAP :: Many small transactional operations vs large analytical scans. Different engines, different storage layouts.
[ ] Row store vs column store :: Row layout suits point reads and writes; columnar layout suits aggregations over few columns of many rows.
[ ] Data lake / warehouse / lakehouse :: Raw storage, modeled analytics store, and the hybrid that adds table semantics over object storage.
[ ] Erasure coding :: Splitting data into fragments plus parity so it survives failures with far less overhead than full replication.
[ ] TTL / expiry :: Automatic removal after a duration. Cheap retention policy for sessions, caches, and time-series data.

## Caching & Performance | zap | concept
[ ] Cache-aside (lazy loading) :: App checks cache, misses, reads the DB, then populates the cache. The default pattern.
[ ] Read-through :: The cache itself loads from the store on a miss, so the app only ever talks to the cache.
[ ] Write-through :: Write to cache and store synchronously. Consistent, slower writes.
[ ] Write-behind (write-back) :: Write to cache and flush to the store asynchronously. Fast, but data can be lost on failure.
[ ] Write-around :: Write straight to the store and let the cache fill on read. Avoids polluting cache with write-once data.
[ ] Eviction policies :: LRU, LFU, FIFO, ARC, and random. Choose by access pattern, not by habit.
[ ] Cache stampede / thundering herd :: A hot key expires and thousands of requests hit the DB at once. Fix with locks, early recompute, and TTL jitter.
[ ] Cache penetration :: Requests for keys that do not exist bypass the cache every time. Fix with negative caching or a bloom filter.
[ ] Cache avalanche :: Many keys expiring together (or a cache node dying) collapses onto the database. Fix with staggered TTLs and warmup.
[ ] Negative caching :: Caching "not found" for a short TTL to absorb junk traffic.
[ ] Cache invalidation :: TTL, explicit purge, versioned keys, or event-driven invalidation via CDC. Famously the hard part.
[ ] Hit ratio :: Hits / total lookups. A low ratio usually means wrong key granularity or a TTL that is too short.
[ ] CDN edge caching :: Serving static and cacheable dynamic content from a POP near the user. Governed by Cache-Control and surrogate keys.
[ ] Cache-Control / stale-while-revalidate :: Directives that let the edge serve slightly stale content instantly while refreshing in the background.
[ ] Latency vs throughput :: Time for one operation vs operations per second. Optimizing one often degrades the other.
[ ] Tail latency (p95/p99) :: The slow requests that define user experience. Averages hide them; always chart percentiles.
[ ] Tail amplification :: A page fanning out to 50 services makes a p99 backend a near-certain slow page. Hedged requests help.
[ ] Little law :: Concurrency = arrival rate x latency. Tells you how many in-flight requests your pool must hold.
[ ] Amdahl / Universal Scalability Law :: Speedup is capped by the serial fraction, and contention plus coherence can make more nodes slower.
[ ] Connection reuse / keep-alive :: Avoiding repeated TCP+TLS handshakes is often the single cheapest latency win.
[ ] Compression :: gzip, brotli, zstd. Trades CPU for bytes on the wire; pick per content type and cacheability.
[ ] Batching vs streaming :: Fewer, larger operations amortize overhead; streaming lowers time-to-first-byte and memory.
[ ] Cold start :: First-invocation penalty in serverless or JIT runtimes. Mitigate with provisioned concurrency and warmup.
[ ] GC pause :: Stop-the-world garbage collection showing up as a latency spike. Tune heap or move to a low-pause collector.
[ ] Zero copy :: Moving data without user-space copies (sendfile, mmap). One reason Kafka is fast.

## Security, Auth & Identity | lock | concept
[ ] AAA (Authentication, Authorization, Accounting) :: Who are you, what may you do, and what did you actually do. Every access system needs all three.
[ ] AuthN vs AuthZ :: Authentication proves identity; authorization decides permission. Different failures, different fixes.
[ ] Session :: Server-side state keyed by an opaque cookie. Instantly revocable, needs shared storage to scale.
[ ] Cookie :: Small key/value the browser resends per request. Secure, HttpOnly, SameSite, Domain, and Path decide how safe it is.
[ ] Token :: A bearer credential sent (usually) in the Authorization header. Whoever holds it can use it — so keep the TTL short.
[ ] JWT :: Signed JSON (header.payload.signature). Stateless and self-describing, but hard to revoke before expiry.
[ ] PASETO :: A JWT alternative with fixed, safe algorithms — no "alg: none" style footguns.
[ ] Refresh token rotation :: Each refresh issues a new token and invalidates the old one; reuse of an old token signals theft.
[ ] OAuth 2.0 / 2.1 :: Delegated authorization. Authorization code + PKCE is the correct flow for web and mobile; implicit is dead.
[ ] OIDC :: An identity layer on top of OAuth 2.0 that adds the ID token — OAuth authorizes, OIDC authenticates.
[ ] SSO :: One login across many applications, usually via SAML or OIDC with a central identity provider.
[ ] SAML :: XML-based enterprise SSO. Still ubiquitous in B2B and legacy corporate environments.
[ ] MFA / TOTP :: A second factor. TOTP derives a 6-digit code from a shared secret plus current time (RFC 6238).
[ ] Passkeys / WebAuthn :: Public-key credentials bound to the origin and stored in the device authenticator. Phishing-resistant, passwordless.
[ ] RBAC / ABAC / ReBAC :: Roles, attributes, or relationships as the basis of permission decisions. ReBAC (Zanzibar-style) handles sharing graphs.
[ ] Principle of least privilege :: Grant the minimum access needed, for the shortest time. The cheapest blast-radius reduction there is.
[ ] Hashing vs encryption vs encoding :: One-way, reversible with a key, and reversible with no secret at all. Base64 is not security.
[ ] Salt and pepper :: A per-user random salt defeats rainbow tables; a global secret pepper adds protection if the DB alone leaks.
[ ] bcrypt / scrypt / argon2 :: Deliberately slow, memory-hard password hashes. Never store passwords with SHA-256 alone.
[ ] HMAC signature :: Keyed hash proving a payload came from someone holding the secret. Standard for webhook verification.
[ ] Digital signature :: Asymmetric signing: private key signs, public key verifies. Gives authenticity plus non-repudiation.
[ ] Nonce / replay attack :: A one-time value plus timestamp so a captured request cannot be replayed later.
[ ] CSRF :: A third-party site triggers an authenticated request. Defend with SameSite cookies plus anti-CSRF tokens.
[ ] XSS :: Injected script executing in your origin. Defend with output encoding, a strict CSP, and no innerHTML on user input.
[ ] SQL injection :: Untrusted input becoming SQL. Parameterized queries are the fix; escaping by hand is not.
[ ] SSRF :: Tricking your server into calling internal addresses. Block link-local metadata IPs and use an egress allowlist.
[ ] IDOR :: Object IDs accepted without an ownership check. Always authorize the object, not just the endpoint.
[ ] Zero trust :: Never trust the network. Authenticate and authorize every request, even service-to-service (mTLS + policy).
[ ] Secrets management :: Central vault, short-lived dynamic credentials, and rotation. Never a .env in git.
[ ] Encryption at rest / in transit :: Disk and field-level encryption plus TLS everywhere — with envelope encryption and a managed KMS.
[ ] PII and data minimization :: Collect the least, retain it the shortest, and know exactly where it lives before someone asks you to delete it.
[ ] Rate limiting as a security control :: Blunts credential stuffing, enumeration, and scraping — not just capacity protection.
[ ] Audit log :: Immutable record of who did what, when, from where. The Accounting in AAA, and the first thing an incident needs.

## Distributed Systems | layers | concept
[ ] Consensus (Raft / Paxos) :: Getting a replica set to agree on an ordered log despite failures. Underpins etcd, Consul, and most control planes.
[ ] Leader election :: Choosing one node to coordinate. Needs fencing so a stale leader cannot keep acting after losing the lease.
[ ] Split brain :: Two nodes both believing they are leader after a partition. Quorums and fencing tokens prevent it.
[ ] Fencing token :: A monotonically increasing number attached to lock holders so storage can reject writes from an expired holder.
[ ] Distributed lock :: Mutual exclusion across processes (Redis, etcd, ZooKeeper). Correct only with leases, fencing, and clock awareness.
[ ] Lease :: A lock with an expiry, so a crashed holder cannot block the system forever.
[ ] Heartbeat / failure detector :: Periodic liveness signals. Tuning the timeout trades false positives against slow detection.
[ ] Gossip protocol :: Nodes exchange state with random peers so membership converges without a central registry.
[ ] Vector clock / Lamport timestamp :: Logical clocks capturing causal ordering when wall clocks cannot be trusted.
[ ] Clock skew / leap second :: Physical clocks drift and jump. Never derive correctness from wall-clock comparisons across machines.
[ ] Eventual consistency :: Replicas converge if writes stop. Perfectly fine for feeds and counters, wrong for balances.
[ ] Strong consistency / linearizability :: Every read sees the latest committed write — as if there were a single copy.
[ ] Read-your-writes / monotonic reads :: Session guarantees that stop a user seeing their own update disappear on the next page load.
[ ] CRDT :: Data types that merge concurrent edits deterministically without coordination. The core of collaborative editing.
[ ] Two-phase commit (2PC) :: Prepare then commit across resources. Correct but blocking — avoid across microservice boundaries.
[ ] Saga :: A long-lived transaction as a sequence of local transactions with compensating actions on failure.
[ ] CQRS :: Separate write model and read model, each optimized for its own shape and scaling profile.
[ ] Event sourcing :: Persist the events, derive state by replaying them. Full audit history at the cost of query complexity and versioning.
[ ] Idempotent receiver :: Deduplication on the consumer so retried deliveries do not double-apply.
[ ] Hinted handoff / read repair :: Availability tricks: hold writes for a down replica, and fix stale replicas discovered during reads.
[ ] Anti-entropy :: Background reconciliation (often Merkle trees) that repairs divergence between replicas.
[ ] Quorum :: A majority overlap of replicas that guarantees any read sees the latest acknowledged write.
[ ] Partition tolerance :: The system keeps operating despite dropped messages between nodes. Not optional in practice.
[ ] Blast radius :: How much fails when one thing fails. Cells, shards, and bulkheads exist to shrink it.
[ ] Cell-based architecture :: Independent full-stack cells serving slices of traffic, so an outage cannot span all users.
[ ] Graceful degradation vs cascading failure :: Shedding load early keeps the core alive; unbounded queues and retries turn one slow service into a full outage.
[ ] Chaos engineering :: Deliberately injecting failure in production-like conditions to validate your assumptions before reality does.

## Observability & Delivery | eye | concept
[ ] SLI / SLO / SLA :: What you measure, the target you commit to internally, and the contract with penalties externally.
[ ] Error budget :: The allowed unreliability inside an SLO. Burn it and feature work pauses for reliability work.
[ ] Logs vs metrics vs traces :: Discrete events, aggregated numbers over time, and the causal path of one request across services.
[ ] Structured logging :: Machine-parseable key/value logs. Free-text logs cannot be queried, aggregated, or alerted on reliably.
[ ] Correlation / trace ID :: An ID propagated through every hop so one user action can be reconstructed end to end.
[ ] Span :: A single timed operation within a trace, with parent/child relationships and attributes.
[ ] Cardinality explosion :: High-variance labels (user ID, URL with IDs) multiplying time series until the metrics bill outruns the app bill.
[ ] Sampling :: Keeping a representative subset of traces or logs. Tail-based sampling keeps the interesting slow/failed ones.
[ ] RED / USE method :: Rate, Errors, Duration for services; Utilization, Saturation, Errors for resources.
[ ] Golden signals :: Latency, traffic, errors, saturation — the four dashboards to build first.
[ ] Alert fatigue :: Too many noisy alerts training humans to ignore the real one. Alert on symptoms and SLO burn rate, not every spike.
[ ] Runbook / playbook :: The written steps for an on-call responder. If an alert has no runbook, it should not page anyone.
[ ] Postmortem (blameless) :: Structured incident review focused on systemic causes and concrete action items, not individuals.
[ ] MTTR / MTBF :: Mean time to recovery and between failures. Reducing MTTR usually beats chasing zero failures.
[ ] Health checks :: Liveness (restart me), readiness (send me traffic), startup (I am still booting). Conflating them causes restart loops.
[ ] Graceful shutdown :: Stop accepting new work, drain in-flight requests, close connections, then exit within the termination grace period.
[ ] Blue-green deployment :: Two identical environments; flip traffic at once, roll back by flipping again.
[ ] Canary release :: Route a small percentage of traffic to the new version, watch metrics, then ramp or abort.
[ ] Rolling update / surge :: Replace instances gradually with controlled maxSurge and maxUnavailable.
[ ] Feature flag :: Decouple deploy from release; ship dark, enable per cohort, and kill instantly without a rollback.
[ ] Immutable infrastructure :: Never patch a running box — build a new image and replace it. Eliminates configuration drift.
[ ] IaC (infrastructure as code) :: Declarative, version-controlled, reviewable infrastructure (Terraform, Pulumi, CDK).
[ ] GitOps :: Git as the single source of truth; a controller continuously reconciles the cluster to the committed state.
[ ] Autoscaling (HPA / VPA / cluster) :: Scale replicas out, resources up, or nodes in the pool — driven by metrics with sensible cooldowns.
[ ] Load shedding :: Rejecting low-priority work early under overload so critical paths keep succeeding.
[ ] Disaster recovery: RTO / RPO :: How fast you must be back, and how much data you can afford to lose. They dictate the backup architecture.
[ ] 12-factor app :: Config in the environment, stateless processes, disposability, dev/prod parity — the baseline for cloud-native services.
